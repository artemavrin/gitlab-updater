# gitlab-updater — план приложения

Статус: план (код не написан). Репозиторий пуст, делаем с нуля.
Цель: **максимально быстро и безопасно обновить локальный self-managed GitLab Omnibus** на Ubuntu/Debian.

---

## 1. Принципы (из них выводится всё остальное)

1. **Правда важнее автоматики.** Инструмент, который честно показывает план и упирается в проблему до старта, ценнее того, который «сам всё сделает» и упадёт на середине.
2. **Быстро = меньше шагов и меньше лишней работы на шаге**, а не «пропустить проверки». Основные пожиратели времени — полный бэкап и background-миграции. Экономим на первом, на втором — нельзя.
3. **Откат = только восстановление из бэкапа.** Downgrade пакета невозможен: миграции БД необратимы. Это пишем пользователю прямым текстом, а не мелким шрифтом.
4. **Ноль внешних зависимостей.** Node ≥ 20, только stdlib (`util.parseArgs`, `styleText`, `node:test`). На проде не должно быть `npm install`, прокси, node_modules. Доставка: `git clone` / `scp` одной папки → `sudo node bin/gitlab-upgrade.js`.
5. **Всё внешнее — через один слой.** Ни одного `execSync` вне `src/core/exec.js`. Это даёт честный dry-run, полный журнал и тестируемость без GitLab.
6. **Версии и матрицы — это данные, а не код.** `data/*.json` с полем `source` + `verified_at`, отдельная команда обновления из upstream.

## 2. Отличия от спеки v2.1 и почему

| Спека | Решение | Причина |
|---|---|---|
| Upgrade path зашит в код | `data/upgrade-path.json` + `--refresh-path` (тянет официальный `config/upgrade_path.yml`) | Зашитый список протухает каждый квартал и врёт молча |
| chalk + meow | stdlib | На закрытом контуре npm-установка — отдельная боль и риск |
| Бэкап полный перед каждым stop | Полный — один раз перед стартом; перед каждым stop — **быстрый** (`SKIP=registry,artifacts,uploads,lfs,packages,builds,pages` + конфиги) | Апгрейд меняет только БД и код. Репозитории и блобы шаги не трогают. Это главный выигрыш по времени (часы → минуты) без потери безопасности |
| Runner через GitLab API + токен | Только локальный пакет `gitlab-runner`; удалённые — отчёт без токена (по имени/версии из `gitlab-rails runner`, если доступно) | Токен админа на диске ради косметики — плохой размен |
| Оценка времени по эвристикам | Заменяю на **измеренный прогресс**: «миграций осталось N, за последние 10 мин закрыто M, темп → ~X» | Эвристики по числу проектов дают ложную точность; реальный счётчик — честный |
| `--force` игнорирует warnings | Оставляю, но `--force` **не** снимает critical и **не** снимает failed-миграции | Иначе флаг превращается в кнопку «сломать данные» |
| Health-check «Redis/PG отвечают» | + отдельно: **failed batched migrations = critical stop** | Спека это упускает; продолжать апгрейд с failed-миграцией — прямой путь к порче данных |
| — | + проверка `unattended-upgrades` / `apt-daily` и apt-lock | Реальная причина зависаний unattended-запуска |
| — | + `DEBIAN_FRONTEND=noninteractive`, `--force-confold` | Иначе dpkg спросит про `gitlab.rb` и повиснет навсегда |
| — | + предупреждение про SSH-сессию (нет tmux/screen/systemd-run) | Обрыв SSH на 6-часовом апгрейде = убитый процесс на миграциях |
| — | + `apt-mark hold` после завершения | Чтобы `apt upgrade` завтра не увёз GitLab на неподдерживаемую версию |

## 3. Архитектура

```
bin/gitlab-upgrade.js        # entrypoint: парсинг флагов → orchestrator, без логики
src/cli/
  options.js                 # определение флагов, дефолты, валидация комбинаций
  render.js                  # вывод плана/чеклиста/прогресса (ru), --json
src/core/
  exec.js                    # ЕДИНСТВЕННАЯ точка запуска команд
  logger.js                  # консоль + JSONL-журнал /var/log/gitlab-upgrade/run-<ts>.jsonl
  state.js                   # state-файл, атомарная запись, resume
  lock.js                    # flock — запрет двух одновременных запусков
  errors.js                  # CriticalError / WarnError, коды выхода
src/detect/
  os.js                      # /etc/os-release
  gitlab.js                  # версия + edition (dpkg-query → VERSION-файл → эвристика)
  services.js                # gitlab-ctl status, версии PostgreSQL / Redis
  apt.js                     # madison, доступность репозитория, apt-locks, таймеры
  disk.js                    # df по точкам монтирования, оценка размера данных
src/plan/
  path.js                    # required stops → список конкретных версий пакетов
  osMatrix.js                # ограничение по ОС
  dbMatrix.js                # требования GitLab → PostgreSQL
  planner.js                 # сборка итогового плана + причины ограничений
src/checks/
  index.js                   # реестр; каждая проверка = чистая функция → Finding
  *.js                       # disk, health, migrations, apt, db, os, session, runner
src/steps/
  backup.js                  # gitlab-backup + конфиги + hook
  install.js                 # apt-get install конкретной версии
  settle.js                  # ожидание сервисов + batched migrations
  verify.js                  # post-step health snapshot
src/run/
  orchestrator.js            # цикл по stops, state, notify, обработка ошибок
src/notify/
  index.js, telegram.js, slack.js, webhook.js
data/
  upgrade-path.json
  os-matrix.json
  pg-requirements.json
test/
  fixtures/                  # записанные выводы реальных команд
  *.test.js                  # node:test
```

### 3.1 `core/exec.js` — узкое место, через которое проходит всё

```js
exec(argv, { cwd, timeout, env, sensitive, mode })
  → { code, stdout, stderr, durationMs }
```

Обязанности:
- режимы: `real` | `dry` (не запускает изменяющие команды, но **запускает читающие** — иначе dry-run врёт) | `replay` (из фикстур, для тестов);
- каждая команда — массив argv, **никакого shell-конкатенирования** (нет инъекций через `--backup-dir`);
- таймаут по умолчанию + отдельный «долгий» режим для install/backup со стримингом вывода в журнал;
- редакция секретов (`GITLAB_TOKEN`, telegram token, webhook URL) в журнале — по списку `sensitive`;
- каждая команда пишется в JSONL до запуска и после (чтобы при `kill -9` было видно, на чём стояли).

Разделение read/write команд задаётся декларативно: у каждой обёртки в `detect/` стоит `readOnly: true`. Это делает `--dry-run` действительно безопасным по построению, а не по внимательности автора.

### 3.2 Единый формат находки (Finding)

```js
{ id, title, level: 'ok'|'warn'|'critical', detail, hint, blocking }
```

Все проверки, все шаги и планировщик возвращают это. Отсюда бесплатно получаются: сводная таблица в dry-run, gating в `--auto`, тело уведомления, `--json` для внешнего мониторинга.

## 4. Данные

### `data/upgrade-path.json`
```json
{
  "source": "https://gitlab.com/gitlab-org/gitlab/-/raw/master/config/upgrade_path.yml",
  "verified_at": "YYYY-MM-DD",
  "stops": ["13.1","13.8","13.12","14.0","14.3","14.9","14.10","15.0","15.4","15.11",
            "16.3","16.7","16.11","17.3","17.5","17.8","17.11","18.2","18.5","18.8","18.11"]
}
```
Команда `gitlab-upgrade refresh-path` скачивает upstream-файл, показывает diff и предлагает записать. Если данные старше N дней — предупреждение в dry-run. Зашитый в код список — нет.

### `data/os-matrix.json`
Ubuntu 16.04/18.04/20.04/22.04/24.04, Debian 10–12 → максимальная поддерживаемая minor.
**Важно:** матрица — только для *раннего понятного сообщения*. Настоящая проверка совместимости — наличие пакета в `apt-cache madison` для текущего дистрибутива репозитория. Матрица может врать, apt — нет.

### `data/pg-requirements.json`
GitLab minor → минимальная версия PostgreSQL (например: 14.0→12, 16.0→13, 17.0→14). Проверяется против **конечной** версии пути, а не только следующего шага, — иначе узнаём о проблеме за пять шагов до неё.

## 5. Планировщик

Вход: `from` (обнаружено или `--from`), `edition`, ОС, флаги `--target-major` / `--safe-for-os` / `--target <ver>`.

1. Нормализовать текущую версию (`17.11.4-ee.0` → `17.11.4`).
2. **Шаг 0:** если текущая версия не последний патч своей minor — сначала подняться до последнего патча (требование GitLab, часто забываемое).
3. Взять stops строго больше текущей minor.
4. Обрезать по `min(--target-major, --safe-for-os, последний доступный в репозитории)`.
5. Для каждого stop — найти **последний доступный патч** через `apt-cache madison gitlab-ee` (parse `17.11.4-ee.0`). Нет патча для stop → critical: путь оборван, дальше идти нельзя.
6. Последним шагом — последняя доступная версия в пределах цели (не обязательно stop).
7. Вернуть план с **причиной** каждого ограничения: «Останавливаемся на 17.11.6, потому что Ubuntu 20.04 (см. `--safe-for-os`)».

Отдельно фиксируется инвариант: **edition (ee/ce) не меняется на всём пути**. Смена — critical.

## 6. Preflight (до первого изменения)

Порядок дешёвых→дорогих, останавливаемся на первом critical:

| Проверка | Critical, если |
|---|---|
| root | не root |
| Omnibus single-node | найден docker/helm/kubernetes-деплой |
| `gitlab-ctl status` | ключевые сервисы (postgresql, redis, gitaly, puma/unicorn, sidekiq) не `run` |
| **failed batched migrations** | есть хоть одна `failed` — **не лечится `--force`** |
| pending batched migrations | есть незавершённые до старта |
| диск | `< --min-free-gb` (5 ГБ) на `/var/opt/gitlab`, `< 3 ГБ` на `/`; отдельно — места под бэкап < оценки |
| apt | репозиторий packages.gitlab.com недоступен / `madison` пуст |
| apt-lock, apt-daily.timer, unattended-upgrades | активны → предложить остановить на время (с восстановлением после) |
| PostgreSQL | версия ниже требуемой **конечной** версией пути |
| ОС-матрица | цель выше потолка ОС и не задан `--safe-for-os` |
| секреты | нет `/etc/gitlab/gitlab-secrets.json` (без него бэкап не восстанавливается) |
| сессия | интерактивный TTY без tmux/screen/systemd → **warn** с конкретной подсказкой |
| `gitlab-rake gitlab:check` | только как warn-источник (шумный), не как гейт |

`--force` снимает warn'ы. Critical не снимает ничего, кроме отдельных явных флагов (`--skip-disk-check`, `--skip-backup`), каждый из которых печатает, чем именно рискует пользователь.

## 7. Шаг апгрейда (для каждого stop)

```
a. disk re-check (данные выросли с прошлого шага)
b. backup:
     шаг 1 → полный (gitlab-backup create STRATEGY=copy)
     шаги 2..N → быстрый (SKIP=registry,artifacts,uploads,lfs,packages,builds,pages)
     всегда → cp gitlab.rb + gitlab-secrets.json в <backup-dir>/<ts>/
     всегда → --backup-hook (LVM/ZFS/VM-снапшот), код ≠ 0 → stop
c. install: DEBIAN_FRONTEND=noninteractive apt-get install -y \
       -o Dpkg::Options::=--force-confold gitlab-ee=<точная версия>
d. settle:
     ждём gitlab-ctl status = все run
     ждём batched migrations: queued == 0
     failed > 0 → CRITICAL STOP (не ждать, не продолжать)
     прогресс каждые 10 мин: осталось N, темп M/10мин, notify если > порога
e. verify: короткий health snapshot (status + версия + миграции)
f. state.save({ completed: stop, backup: path, ts })
g. notify «шаг K/N готов»
```

Финал: обновление локального runner'а (если включено) → финальный health-check → `apt-mark hold` → notify «успех» → очистка state.

**Что делает это быстрым:** один полный бэкап вместо N, отсутствие интерактивных промптов dpkg, отсутствие простоя между шагами на ручное подтверждение, параллельно ничего — но и ждём мы ровно то, что обязаны ждать.

## 8. State, resume, блокировка

- `/var/lib/gitlab-upgrade/state.json` (не `/var/tmp` — там чистка по крону).
- Атомарная запись: temp + `rename`.
- `flock` на `/var/lib/gitlab-upgrade/lock` — два экземпляра не запустятся.
- В state: план целиком, индекс текущего шага, фаза внутри шага, пути бэкапов, PID, версия инструмента.
- При старте с существующим state: **не продолжать вслепую** — перепроверить реальную версию GitLab на диске и сверить с ожидаемой. Разошлось → показать расхождение и потребовать `--resume` / `--restart`.
- `kill -9` на фазе миграций → повторный запуск подхватывает ожидание, а не переустанавливает пакет.

## 9. CLI

```
sudo node bin/gitlab-upgrade.js [команда] [опции]

Команды:
  plan            (по умолчанию) обнаружение + проверки + план, ничего не меняет
  run             выполнить апгрейд (требует --yes)
  resume          продолжить прерванный запуск
  refresh-path    обновить data/upgrade-path.json из upstream
  doctor          только проверки, без плана

Цель:
  --from <ver>            принудительно задать текущую версию
  --to <ver>              конечная версия
  --target-major <n>      верхняя граница major
  --safe-for-os           не выше потолка текущей ОС (берётся min со всеми ограничениями)

Бэкап:
  --backup / --no-backup            (по умолчанию вкл.)
  --backup-mode full|fast|first-full   (по умолчанию first-full)
  --backup-dir <path>
  --backup-hook <script>
  --skip-backup                     явный риск, печатает предупреждение

Проверки:
  --min-free-gb <n>        (5)
  --skip-disk-check, --skip-health-check, --skip-db-check
  --force                  игнорировать warn (не critical)
  --pg-upgrade             разрешить gitlab-ctl pg-upgrade в безопасной точке

Прочее:
  --yes, -y                подтверждение изменяющих действий
  --notify / --no-notify   (env: TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID, SLACK_WEBHOOK_URL, NOTIFY_WEBHOOK_URL)
  --update-runners / --no-update-runners
  --json                   машинный вывод плана/статуса
  --log-dir <path>
```

Дефолт без аргументов — `plan`. Ничего разрушительного без `run --yes`.

## 10. Тестирование (без живого GitLab)

1. **Фикстуры.** `test/fixtures/` — записанные реальные выводы `dpkg-query`, `apt-cache madison`, `gitlab-ctl status`, `df`, `os-release` для нескольких сценариев (13.12/Ubuntu 18.04, 15.11/20.04, 17.8/22.04, сломанный инстанс).
2. **`exec` в режиме replay** — прогоняем весь оркестратор целиком на фикстурах, включая ветки ошибок. Покрывает планировщик, проверки, state/resume, форматирование.
3. **Property-тест планировщика:** для любой стартовой версии путь монотонно возрастает, содержит все обязательные stops между началом и концом, не пропускает ни одного.
4. **Тест resume:** прерывание на каждой фазе каждого шага → повторный запуск не переустанавливает и не теряет шаг.
5. **Опционально, phase 3:** докер-репетиция на `gitlab/gitlab-ee:<старая версия>` — реальный прогон короткого пути. Дорого, но один раз перед боевым запуском окупается.

## 11. Фазы (в порядке «быстрее всего до пользы»)

| Фаза | Содержание | Ценность |
|---|---|---|
| **0** | exec/logger/state/detect + планировщик + `plan` | Пользователь видит правдивый план для **своего** сервера. Риск нулевой |
| **1** | Preflight-проверки + `doctor` | Ловим 90% причин падения в середине — до старта |
| **2** | backup → install → settle → state/resume, `run --yes` | Собственно апгрейд, unattended |
| **3** | Уведомления (Telegram/Slack/webhook) | Можно уйти |
| **4** | Runner, `--pg-upgrade`, прогресс-темп миграций | Полировка |

Фазы 0–2 — это работающий продукт. 3–4 добавляются без переделки ядра.

## 12. Честные ограничения

- **Отката нет.** Только восстановление из бэкапа + `gitlab-secrets.json`. Реальный откат — снапшот VM/LVM до старта; для этого есть `--backup-hook`. Пишем это в выводе перед первым шагом, а не в README.
- Ubuntu инструмент **не обновляет**. Упёрлись в потолок ОС — останавливаемся и объясняем.
- Только Omnibus, один узел. Docker/Helm/multi-node — определяем и отказываемся, а не «пробуем».
- Оценка времени — порядок величины, помечается как приблизительная; точный сигнал — счётчик оставшихся миграций.
- `apt-cache madison` — источник истины по доступности; если репозиторий packages.gitlab.com недоступен, инструмент бесполезен и честно об этом говорит.
