# gitlab-updater — UI

React + Ink для интерактивной поверхности. Ниже — что это значит архитектурно и как выглядит каждый экран.

---

## 1. Ink и требование «ноль зависимостей на сервере»

Противоречия нет, если разделить сборку и запуск:

- **В исходниках** — `react` + `ink` (и только они; примитивы select/input/spinner пишем свои, ~120 строк на все, чтобы не тянуть цепочку мелких пакетов на закрытый контур).
- **На сервере** — один файл. `npm run build` → esbuild → `dist/gitlab-upgrade.mjs`. Никакого `node_modules`, `npm install` через прокси и разъезда версий.

Деплой: `scp dist/gitlab-upgrade.mjs server:` → `sudo node gitlab-upgrade.mjs plan`.
`dist/` коммитим только на тегах релиза — чтобы не шуметь диффом в обычных PR, но чтобы на изолированной машине хватило `git clone` без сборки.

---

## 2. Ядро не знает про UI

Это главное следствие Ink. Оркестратор не печатает — он **испускает события**:

```js
bus.emit({ t: 'step:start',   step: 3, version: '16.11.10-ee' })
bus.emit({ t: 'phase:ok',     phase: 'backup', size: 2.1e9, ms: 192000, path: '...' })
bus.emit({ t: 'migrations',   remaining: 47, closedLast10m: 8 })
bus.emit({ t: 'interrupt',    safe: false, why: 'идёт dpkg' })
```

```
Core ──► EventBus ──┬──► JSONL-журнал на диске   (источник правды)
                    └──► Renderer
                           ├─ Ink        TTY
                           ├─ Plain      нет TTY, --plain, вывод в файл
                           └─ JSON       --json, для мониторинга
```

Три следствия:

1. **`> log.txt` даёт нормальный лог**, а не мусор из перерисовок. Fullscreen-TUI в редиректе — классическая беда Ink-приложений; здесь её нет по построению.
2. **`attach` почти бесплатен.** Журнал на диске — источник правды, значит отдельный процесс может его читать и рисовать тот же экран. `run --detach` уходит под `systemd-run`, `gitlab-upgrade attach` подключается. **Обрыв SSH больше не убивает шестичасовой апгрейд** — это не косметика, а главная причина испорченных апгрейдов по SSH.
3. **UI тестируется** — `ink-testing-library` рендерит в строку, снапшотим экраны на записанных потоках событий.

## 3. Правила оформления

| | |
|---|---|
| Ширина | работает от 80 колонок, использует до 120 |
| Цвет | 4 роли: `ok` зелёный, `warn` жёлтый, `critical` красный, `dim` серый; `accent` голубой — только текущий элемент |
| `NO_COLOR`, `--no-color` | уважаем |
| Рамки | нет. Разделитель — пустая строка. Отступ слева 1 пробел |
| Спиннер | максимум один на экран — тот, что действительно работает сейчас |
| Язык | русский и английский; колонки считаются от подписей активной локали, не константами |

Про язык отдельно: `pad(label, 27)` в макетах ниже — сокращение записи, а не спецификация. `место на диске` и `disk space` отличаются вдвое, поэтому в коде ширина колонки — `Math.max(...labels.map(len)) + 2` по фактическим строкам локали. Отсюда обязательный тест: снапшот каждого экрана в каждой локали с проверкой, что ни одна строка не длиннее 78 колонок.

Смысл ограничений: экран обновляется каждую секунду часами подряд. Всё, что мигает и перерисовывается без нужды, за шесть часов превращается в раздражитель.

## 5. `run` — основной экран: лента

**Утверждено.** Экран `run` — прокручиваемый поток, а не фиксированный кадр. Живёт только закреплённая строка внизу; всё остальное — история, которую можно отмотать.

```
 13:31:20  шаг 1/6  16.3.9-ee
   ✓ бэкап полный              187 ГБ · 79 мин
   ✓ установка пакета          из кэша · 7 мин
   ✓ фоновые миграции          132 → 0 · 41 мин
 15:38:47  шаг 1/6 готово за 02:07:27

 15:38:48  шаг 2/6  16.7.10-ee
   ✓ бэкап быстрый             1.9 ГБ · 3 мин
   ✓ установка пакета          из кэша · 5 мин
   ✓ фоновые миграции          88 → 0 · 30 мин
 16:19:55  шаг 2/6 готово за 00:41:07

 16:19:56  шаг 3/6  16.11.10-ee
   ✓ место на диске            139 ГБ свободно
   ✓ бэкап быстрый             2.1 ГБ · 3 мин · …/gitlab/20260830-1412
   ✓ установка пакета          из кэша · 6 мин
   ✓ сервисы                   12/12 running
   ⠋ фоновые миграции          осталось 47 · −8 за 10 мин
     14:54:12  BackfillProjectStatistics       23%
     14:54:51  осталось 47
──────────────────────────────────────────────────────────────────────────────
 шаг 3/6 · 01:47:12 · миграции 47 · Ctrl-C безопасен          [p] путь
```

Почему поток, а не панель:

- **Скроллбэк цел.** На пятом часу можно отмотать к первому шагу. Фиксированный кадр эту историю уничтожает.
- **Форма знакома.** Так ведут себя `apt`, `docker build`, `cargo`. Учиться нечему.
- **Работает в любом размере окна** — в отличие от кадра, который требует 78×30.
- **Вывод почти совпадает с `--plain`**, а значит `attach` рисует то же, что лежит в JSONL.

Цепочка версий на этом экране отсутствует намеренно: она уехала на отдельный экран (§6). Горизонтальная цепочка в 78 колонках даёт девять символов на шаг — туда не влезает ни длительность, ни размер бэкапа, ни счётчик миграций.

### 5.1 Индикатор безопасности прерывания

Последняя строка меняется по фазе, потому что цена Ctrl-C разная:

```
 шаг 3/6 · 01:47:12 · миграции 47 · Ctrl-C безопасен          [p] путь
 шаг 3/6 · 01:31:40 · установка   · Ctrl-C опасен · dpkg      [p] путь
```

В опасной фазе Ctrl-C **не убивает процесс молча**, а печатает в ленту:

```
 ⛔ Сейчас идёт установка пакета (dpkg).
    Прерывание оставит систему в незавершённой транзакции dpkg.
    Выходить придётся руками: dpkg --configure -a

    [d]              отсоединиться, апгрейд продолжится
    [Ctrl-C ещё раз] всё равно прервать
```

Это главный довод за TUI в этом инструменте: в три часа ночи человек жмёт Ctrl-C по привычке, и статический вывод его не остановит.

### 5.2 Прогресс миграций — измеренный

`осталось 47 · −8 за 10 мин` — факт, а не эвристика по числу проектов. Темп ноль дольше 30 минут → строка желтеет с подписью «возможно, застряла». Появилась failed → красная и немедленная остановка.

## 6. Экран пути — по `[p]`

**Утверждено:** вертикальный рельс, одна строка на шаг, выбранный шаг разворачивается.

```
 Путь апгрейда                                       [p] вернуться в ленту
 15.11.13-ee → 17.11.6-ee · шаг 3 из 6 · прошло 03:30:12

  ●  16.3.9-ee      готово   2:07:27   187 ГБ  132 → 0
  ●  16.7.10-ee     готово   0:41:07   1.9 ГБ   88 → 0
 ▸◐  16.11.10-ee    сейчас   0:41:09   2.1 ГБ   51 осталось
  │     бэкап       быстрый · 2.1 ГБ · 16:23:11 · …/20260830-1412
  │     установка   из кэша · 6 мин · gitlab-ee=16.11.10-ee.0
  │     сервисы     12/12 running
  │     миграции    ⠋ осталось 51 · −8 за 10 мин · ~64 мин
  ○  17.3.7-ee      ждёт     ~35 мин   —       —
  ○  17.5.5-ee      ждёт     ~30 мин   —       —
  ○  17.11.6-ee     цель     ~45 мин   —       —

 ↑↓ выбрать шаг · [p] вернуться в ленту
```

Три решения и их основания:

1. **Вертикально.** Терминал построчный. Поперёк на шаг остаётся девять символов; вдоль — целая строка под данные.
2. **Одна строка на шаг, колонки выровнены.** Значения встают друг под друга, поэтому шаги сравнимы: сразу видно, что первый занял 2:07, а второй 0:41.
3. **Раскрытие вместо второй строки у каждого.** Деталь уходит вниз, а не вбок, и потолок ширины перестаёт быть ограничением: влезает время бэкапа, его путь и точное имя пакета. По умолчанию раскрыт текущий шаг — то есть без единого нажатия видно ровно то, что нужно чаще всего.

Цена, которую принимаем осознанно: подробности видны только у одного шага за раз, и экран становится интерактивным (`↑↓`). Для сравнения шагов между собой хватает выровненных колонок в свёрнутых строках.

Маркеры: `●` пройден, `◐` текущий, `○` предстоит, `▸` выбран. Рельс `│` держит блок раскрытия визуально привязанным к своему шагу.

## 7. `config` — экран настроек

**Утверждено:** оглавление из разделов, раздел открывается на весь экран.

```
 Настройки                                    /etc/gitlab-upgrade/config.json

 ▸  ✓  Сеть            socks5h://10.0.0.5:1080 · проверен 2 мин назад
    ✓  Уведомления     Telegram настроен · Slack и webhook не заданы
    ✓  Бэкап           /mnt/backup/gitlab · 240 ГБ свободно
    ✓  Пороги и цель   мин. 10 ГБ · до 17.11.6-ee, 6 шагов

    Всё настроено. Готово к запуску:
      sudo gitlab-upgrade run --yes --detach

 ↑↓ раздел · Enter открыть раздел · [t] проверить раздел
```

`Enter` открывает раздел, где под каждым полем есть место для объяснения:

```
 Настройки › Сеть                                             Esc назад

 ▸  прокси          socks5h://10.0.0.5:1080        конфиг   ✓ работает
                    HTTP или SOCKS5. Через него ходит только apt
                    к packages.gitlab.com — остальное напрямую.

    авторизация     gitlab-svc / ••••••••          конфиг
    режим           auto → bridge                  авто
    CA прокси       не задан                       —
    область         только packages.gitlab.com     дефолт

    ✓ TCP 10.0.0.5:1080              12 мс
    ✓ SOCKS5 handshake               username/password
    ✓ CONNECT packages.gitlab.com    443
    ✓ TLS                            сертификат валиден
    ⠋ apt через прокси

 ↑↓ поле · Enter изменить · [t] проверить · Esc назад
```

Решения:

1. **Первый экран отвечает на главный вопрос — можно ли запускать.** Внизу стоит готовая команда. Опись из четырёх строк читается за секунду; двадцать строк полей — нет.
2. **Колонка «источник» у каждого поля** — `конфиг`, `env`, `флаг`, `дефолт`, `авто`. Это `--explain-config`, встроенный в экран. Половина обращений «оно не видит мою настройку» закрывается тем, что видно: значение пришло из `env`, а под `sudo` окружение другое.
3. **Проверка на месте.** `t` гоняет реальную последовательность (TCP → SOCKS5 → CONNECT → TLS → apt) прямо под полями. Настройка, которая не проходит проверку, не записывается в конфиг.
4. **Место под объяснение.** «CA прокси» и «режим auto → bridge» ничего не говорят человеку, который видит их впервые. В плоском списке для подсказки нет места, в разделе — есть.

Мастер `setup` — тот же экран, пройденный линейно при первом запуске: те же поля, та же проверка после каждого ответа.

## 7A. Компактный экран — профиль `patch`

Повседневное обновление патча — один шаг: ни истории, ни пути, ни счётчика «шаг N из M». Лента и экран пути здесь были бы церемонией вокруг двенадцати минут работы. Профиль `patch` (см. [FLOWS.md](FLOWS.md)) получает свой экран.

Вход — один вопрос:

```
 GitLab 17.11.4-ee → 17.11.6-ee                 патч, та же минорная версия
 gitlab.corp.local · Ubuntu 22.04 · через прокси

   ✓ сервисы 12/12 · миграций в очереди нет · 142 ГБ свободно
   ✓ пакет доступен: 17.11.6-ee.0 · 1.1 ГБ

 Один шаг: бэкап БД и конфигов, установка, миграции.
 Ориентировочно 10–20 минут, GitLab будет недоступен около 2 минут.

 Обновить? [y/N]
```

Ход работы:

```
 17.11.4-ee → 17.11.6-ee                                        00:04:12
   ✓ бэкап БД и конфигов      1.2 ГБ · 1 мин · …/20260830-2103
   ✓ загрузка пакета          1.1 ГБ через прокси · 47 с
   ✓ установка                2 мин
   ✓ сервисы                  12/12 running
   ⠋ фоновые миграции         осталось 3

 Ctrl-C сейчас безопасен
```

Финал — три строки:

```
 ✓ GitLab 17.11.6-ee                                      заняло 00:11:38
   миграции завершены · сервисы 12/12 · бэкап …/20260830-2103
   пакет закреплён: apt-mark hold gitlab-ee
```

Что сохраняется от «большого» режима и почему:

- **Индикатор безопасности `Ctrl-C`** — фаза `dpkg` одинаково опасна для патча и для мажорного апгрейда.
- **Экран остановки (§8) и `resume` (§9)** — те же. Падение на патче встречается реже, но выглядит так же и требует тех же действий.
- **Бэкап** — обязателен, просто дешёвый: БД и конфиги вместо полного, две минуты вместо восьмидесяти.

Что убрано: счётчик шагов, лента с историей, экран пути, предложение `--detach`, уведомления о старте и финише.

## 7B. Блокеры — то, что мешает начать

Экран `run` поднимается на `run:start`, то есть уже после проверок. Всё, что мешает начать, до этой ревизии показывалось плоским списком, где пять critical размазаны между пройденными галочками, а объяснение обрезалось по краю строки.

```
 ⛔ Обновление не начнётся — критических: 2

 ✗ PostgreSQL
    версия 13.11, а 17.11.6-ee требует не ниже 14.14
    Что делать
      sudo gitlab-ctl pg-upgrade
      обновить встроенный PostgreSQL (внешний обновляется иначе)
      подробности:
      https://docs.gitlab.com/omnibus/settings/database/

 ✗ фоновые миграции
    1 упавших: идти дальше нельзя, следующий шаг будет мигрировать поверх
    незавершённых данных
    Что делать
      sudo gitlab-rake gitlab:background_migrations:list
      посмотреть список фоновых миграций и их состояние
      подробности:
      https://docs.gitlab.com/update/background_migrations/

 ✓ пройдено проверок: 8 — права root, GitLab Omnibus, сервисы GitLab, …

   8 пройдено · 0 предупреждений · 2 критических
```

Решения:

1. **Вопрос другой, чем у списка проверок.** Список отвечает «что проверили», этот блок — «что мне сейчас чинить». Поэтому пройденное сворачивается в одну строку: на второй вопрос оно не отвечает.
2. **Команда, а не пересказ.** Берётся из таблицы починок (`src/checks/remedies.js`), сверенной с docs.gitlab.com, и выбирается по установленной версии там, где команда от неё зависит. Где документированной команды нет — ссылка вместо выдуманной строки.
3. **Перенос, а не обрезка.** Резалось именно объяснение, почему нельзя идти дальше.

### Почему это не Ink

Ink рисует живой кадр и ради этого чистит экран вместе со скроллбэком (`ESC[2J ESC[3J`). Для ленты `run` это правильно. Для справки, которая не меняется, — уничтожение истории терминала ровно в тот момент, когда человек хочет её сохранить. Проверено под настоящим pty: Ink чистил экран и печатал блок дважды.

Поэтому блок печатается строками с ролью, а цвет накладывается четырьмя escape-последовательностями (`src/render/color.js`). Разметка при этом одна: `blockerLines()` отдаёт строки, `--plain` склеивает их как есть, терминал — раскрашивает. Цвет включается только когда приёмник — терминал: `doctor > log.txt` даёт текст.

## 8. Остановка — экран, ради которого всё писалось

До этой ревизии в спеке был спроектирован только счастливый путь. Между тем инструмент пишется ровно ради обратного случая: апгрейд упал на середине, три часа ночи, GitLab в промежуточной версии.

Экран отвечает на три вопроса, и именно в этом порядке:

```
   ✓ установка пакета        из кэша · 6 мин
   ✓ сервисы                 12/12 running
   ✗ фоновые миграции        1 миграция упала

──────────────────────────────────────────────────────────────────────────────
```

здесь: rake-задачи для фоновых миграций появились в 18.5 и переименовались
в 18.9 — макет выше показывает форму для 18.9+, а на 16.x инструмент вместо
несуществующей команды даёт ссылку на документацию. При нескольких аргументах
задачи `finalize` запятая между ними экранируется обратным слэшем, иначе rake
отвечает ошибкой про недопустимый символ.

1. **«Работает ли GitLab прямо сейчас».** Блок «Состояние системы» идёт раньше инструкций, потому что это первое, что нужно человеку: можно ли не будить остальных.
2. **«Что именно сломалось».** Имя миграции и текст ошибки БД, а не «ошибка при обновлении».
3. **«Что нажать».** Копируемые команды с аргументами, а не «дожмите миграцию».

Плюс два факта, которые нельзя оставлять на догадки: **откат невозможен** и **где лежит бэкап**. Оба на экране, оба до того, как человек начнёт импровизировать.

## 9. `resume` — никогда не продолжаем вслепую

```
 Найден прерванный запуск
   начат        30.08.2026 13:31:20 · 4 ч 10 мин назад
   остановлен   на шаге 3 из 6 (16.11.10-ee)
   причина      упала миграция BackfillProjectStatistics
   бэкап шага   2.1 ГБ · /mnt/backup/gitlab/20260830-1412

 Сверяю состояние сервера с сохранённым
   ✓ версия GitLab         16.11.10-ee — как в state
   ✓ редакция              ee — не менялась
   ✓ сервисы               12/12 running
   ✓ фоновые миграции      завершены, упавших нет
   ✓ прокси                доступен · 47 версий
   ✓ место                 139 ГБ на /var/opt/gitlab

 Можно продолжить с шага 3. Осталось 4 шага, ~2 ч 40 мин.

   sudo gitlab-upgrade resume --yes      продолжить с шага 3
   sudo gitlab-upgrade plan              пересчитать путь заново
   sudo gitlab-upgrade resume --restart  забыть state, начать сначала
```

Ключевая ветка — расхождение. Между падением и `resume` кто-то мог обновить сервер руками:

```
   ✗ версия GitLab         17.3.7-ee — в state было 16.11.10-ee
   ! фоновые миграции      14 незавершённых

 Состояние разошлось. Сервер обновляли мимо инструмента.

 Продолжать по сохранённому плану нельзя: он рассчитан от 16.11.10,
 а на диске уже 17.3.7. Путь надо пересчитать от того, что есть.

   sudo gitlab-upgrade plan --from 17.3.7   пересчитать от текущей
```

State при этом **не удаляется**: забыть его — отдельное явное действие `--restart`.

## 14. Структура UI-кода

```
src/ui/
  available.js          нужен ли Ink вообще — решается до импорта React
  render.jsx            монтирование экрана на EventBus
  App.jsx               мост «шина → React»
  runState.js           состояние экрана run: чистая функция от потока событий
  theme.js              4 цветовые роли + NO_COLOR
  screens/
    Run.jsx             лента, экран пути, экран прерывания
  components/
    FeedLine.jsx        строка ленты: заголовок шага или фаза
    PathChain.jsx       вертикальный рельс с раскрытием выбранного шага
    SafetyBar.jsx       индикатор безопасности Ctrl-C
    Spinner.jsx         свой, без внешних пакетов
src/render/
  events.js             событие → текст: общий для Ink, plain и attach
  plain.js              не-TTY рендереры на том же потоке событий
```

Экраны — чистые функции от потока событий. Отсюда снапшот-тест: подать
записанный JSONL реального апгрейда → сравнить кадры. Никакого GitLab и
терминала для этого не нужно (`test/ui.test.jsx`, `test/fixtures/run-events.js`).

**Разделение, которого стоило добиться.** `src/render/events.js` — единственное
место, где событие превращается в человеческий текст. Ink и `--plain` обязаны
говорить одно и то же: `attach` рисует журнал идущего апгрейда, и два разных
рассказа об одном апгрейде — худшее, что можно предложить человеку в три часа
ночи. Тест сверяет вывод plain-рендерера со всем, что показал экран за прогон.

### 14.1 Что пришлось решить в сборке

- **Node не умеет `.jsx`.** На сервер уезжает бандл, где JSX уже развёрнут, но
  тесты должны идти без сборки: `scripts/jsx-loader.mjs` регистрирует хуки,
  трансформирующие `.jsx` эсбилдом. В бандл они не попадают.
- **Точка входа импортирует экраны динамически** и молча откатывается на
  построчный вывод, если `.jsx` не загрузился. Шестичасовой апгрейд не должен
  падать из-за формы вывода.
- **Ink тянет `react-devtools-core`** динамическим импортом при `DEV=true`.
  В бандле он подменён заглушкой: 700 КБ ради ветки, которой на сервере не бывает.
- **Транзитивные CJS-зависимости Ink зовут `require()`** внутри ESM-бандла.
  Баннер сборки заводит `createRequire`, иначе первое же обращение к
  `node:assert` роняет процесс.
- **Цена Ink — размер бандла**: 168 КБ → 1.9 МБ. Для одного файла, который
  копируют по scp, это ничто; минификация выключена сознательно.

### 14.2 Ink поднимается лениво

Экран монтируется не при старте команды, а на событии `run:start`. До него
идут проверки и обнаружение версии, и `run` часто упирается в отсутствие
GitLab или занятый лок — очистка экрана ради сообщения об ошибке была бы
чистым шумом. Пока `run:start` не пришёл, терминал не тронут вообще.
