# Сценарии работы

Инструмент обслуживает три разных задачи, а не одну. Разница между ними — не в коде, а в **весе церемонии**: сколько проверять, сколько бэкапить, сколько спрашивать и сколько писать на экран.

---

## 1. Профиль вычисляется, а не выбирается

Пользователь всегда набирает одно и то же. Профиль определяет планировщик, посчитав путь:

```
   путь построен
        │
        ├─ 1 шаг, та же минорная версия        →  patch
        ├─ 1–2 шага, major не меняется         →  minor
        └─ 3+ шага или смена major             →  long
```

Это принципиально: **человек не должен знать, в какой он ситуации** — он для того и запускает инструмент, чтобы тот разобрался. Флаг `--profile` существует только чтобы принудительно поднять вес (`--profile long` на всякий случай), но не понизить: занизить церемонию можно лишь отдельными явными флагами вроде `--skip-backup`, каждый из которых печатает, чем рискует пользователь.

---

## 2. Чем профили отличаются

| | `patch` | `minor` | `long` |
|---|---|---|---|
| Пример | 17.11.4 → 17.11.6 | 17.11 → 18.0 | 15.11 → 17.11 |
| Шагов | 1 | 1–2 | 3+ |
| Порядок времени | 10–20 мин | 30–90 мин | часы |
| Простой сервиса | ~2 мин | 2–5 мин | по 2–5 мин на шаг |
| **Бэкап** | `db` — БД и конфиги, ~2 мин | `db` | первый полный, дальше быстрый |
| **Предзагрузка** | нет | нет | да, весь путь сразу |
| **Health-check** | быстрый: сервисы, миграции, место | полный | полный |
| **Подтверждение** | одна строка `[y/N]` | план + `[y/N]` | план + явный `--yes` |
| **Экран** | компактный (§5) | лента | лента + путь `[p]` |
| **`--detach`** | не упоминаем | предлагаем, если ожидание > 30 мин | настойчиво рекомендуем |
| **Уведомления** | только ошибка | старт, финиш, ошибка | все события |
| **Оценка** | в минутах | в минутах | в часах, помечена как приблизительная |

Что **не** зависит от профиля и работает одинаково везде: прокси, state и `resume`, экран остановки, проверка failed-миграций, `apt-mark hold` в конце, запись журнала.

## 3. Команды

### `check` — есть ли что обновить

Ничего не меняет, ходит только в `apt`. Предназначена для крона и мониторинга.

```
$ sudo gitlab-upgrade check
17.11.6-ee доступна (у вас 17.11.4-ee) · патч · ~10–20 мин
```

Коды возврата:

| код | значение |
|---|---|
| `0` | установлена последняя доступная версия |
| `10` | доступен патч в текущей минорной версии |
| `20` | доступна новая минорная версия |
| `30` | доступна новая мажорная версия |
| `1` | ошибка (нет доступа к репозиторию, не удалось определить версию) |

Это позволяет повесить в cron однострочник и получать письмо только когда есть что делать, либо отдать код в Zabbix/Prometheus через textfile-collector.

### `next` — какую версию ставить прямо сейчас

`plan` отвечает на вопрос «куда мы идём целиком», `next` — на вопрос «что ставить следующим шагом». Второй нужен скриптам, агентам и человеку, который ведёт длинный путь вручную по одному шагу за вечер.

```
$ sudo gitlab-upgrade next --quiet
17.1.8-ee.0
```

Обоснование берётся из официального `upgrade_path.yml`, а не из наших соображений: причина шага, соответствующая остановка, признак условности, дословное примечание первоисточника и ссылка на официальные заметки к мажорной серии. Плюс `source` и `verifiedAt` — ответ можно проверить, не доверяя инструменту на слово.

Коды возврата у `next` описывают **ближайший шаг**, а у `check` — весь разрыв до цели. Это не рассогласование, а разные вопросы: с 16.3 следующий шаг 16.7 минорный, хотя весь путь мажорный. Обе трактовки записаны в каталоге `api`, чтобы агент не гадал.

### `gitlab-upgrade` без аргументов — повседневный вход

Проверка → план → подтверждение → выполнение. Для профиля `patch` это один экран и один вопрос:

```
$ sudo gitlab-upgrade

 GitLab 17.11.4-ee → 17.11.6-ee                 патч, та же минорная версия
 gitlab.corp.local · Ubuntu 22.04 · через прокси

   ✓ сервисы 12/12 · миграций в очереди нет · 142 ГБ свободно
   ✓ пакет доступен: 17.11.6-ee.0 · 1.1 ГБ

 Один шаг: бэкап БД и конфигов, установка, миграции.
 Ориентировочно 10–20 минут, GitLab будет недоступен около 2 минут.

 Обновить? [y/N]
```

Для `minor` и `long` тот же вход показывает полный план и требует `--yes`.

### `--patch-only` — автоматический патчинг

Режим для крона: обновляет только до последнего патча текущей минорной версии и **отказывается** делать что-либо ещё. Вышла новая минорная — молча выходит с кодом `20`, ничего не трогая.

```cron
# каждое воскресенье в 04:00, только патчи, писать в Telegram только при ошибке
0 4 * * 0  /usr/local/bin/gitlab-upgrade --patch-only --yes --plain >> /var/log/gitlab-upgrade/cron.log 2>&1
```

Почему это безопасно автоматизировать, а минорные обновления — нет: патч внутри минорной версии не проходит обязательных остановок, не меняет требований к PostgreSQL и почти никогда не запускает долгие batched-миграции. Всё, что может пойти не так, ловится теми же проверками, а бэкап БД перед ним стоит две минуты.

Ограничения режима остаются жёсткими: failed-миграция до старта — отказ; нет места — отказ; репозиторий недоступен — отказ. Молча пропустить проверку `--patch-only` не позволяет.

## 4. Полный маршрут

```
  gitlab-upgrade check ──── код 0 ──── нечего делать
        │
        код 10/20/30
        │
  gitlab-upgrade ─── определить ОС, версию, редакцию
        │
        ├─ health-check (глубина по профилю)
        ├─ место на диске
        ├─ PostgreSQL против конечной версии пути
        ├─ построить путь → профиль
        └─ проверить наличие пакетов в apt
        │
     показать план ──── [y/N] или --yes ──── отказ → выход 0
        │
      [long] предзагрузить все пакеты
        │
   для каждого шага:
        ├─ проверка места
        ├─ бэкап (режим по профилю) + hook
        ├─ apt-get install <точная версия>
        ├─ дождаться сервисов
        ├─ дождаться миграций ──── failed ──► ЭКРАН ОСТАНОВКИ ──► resume
        └─ сохранить state
        │
   финал: runner → health-check → apt-mark hold → очистить state
```

Единственная ветка, ведущая не в финал, — failed-миграция или критическая проверка. Обе приводят на экран остановки, откуда путь один: починить и `resume`.

## 5. Компактный экран профиля `patch`

Лента с историей и экран пути при одном шаге не нужны — истории нет, пути нет. Вместо них:

```
 17.11.4-ee → 17.11.6-ee                                        00:04:12
   ✓ бэкап БД и конфигов      1.2 ГБ · 1 мин · …/20260830-2103
   ✓ загрузка пакета          1.1 ГБ через прокси · 47 с
   ✓ установка                2 мин
   ✓ сервисы                  12/12 running
   ⠋ фоновые миграции         осталось 3

 Ctrl-C сейчас безопасен
```

Финал — три строки вместо экрана:

```
 ✓ GitLab 17.11.6-ee                                      заняло 00:11:38
   миграции завершены · сервисы 12/12 · бэкап …/20260830-2103
   пакет закреплён: apt-mark hold gitlab-ee
```

Индикатор безопасности `Ctrl-C` остаётся: фаза `dpkg` опасна независимо от того, патч это или мажорный апгрейд.

## 6. Что это меняет в плане реализации

Профили не добавляют новой фазы — они меняют параметры существующих. Конкретно:

- `plan/planner.js` возвращает `profile` вместе с путём;
- `checks/index.js` получает набор проверок по профилю (быстрый набор — подмножество полного);
- `steps/backup.js` получает третий режим `db`;
- `steps/predownload.js` не вызывается при одном шаге;
- `ui/screens/` получает `Compact.jsx` рядом с `Run.jsx`;
- `notify/index.js` фильтрует события по профилю.

Плюс новая команда `check` — самая дешёвая в реализации из всех: детект версии и `apt-cache madison`, без единого изменяющего действия. Её имеет смысл сделать **первой** после ядра: она полезна сама по себе и проверяет весь стек детекта и прокси на реальном сервере, ничего не ломая.
